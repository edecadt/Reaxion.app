# Create a New Service

This repository loads its integrations (“services”) dynamically from the `services/` folder. Each service lives in its own lightweight Node package: the NestJS backend reads the manifest generated by the SDK and automatically exposes the service to the frontend without extra wiring.

## Prerequisites

- Node.js ≥ 18 and `pnpm` (the workspace is managed with `pnpm`).
- Run `pnpm install` at the repository root at least once so the workspace dependencies are installed.
- Optional but recommended: restart `pnpm --filter backend dev` after adding files to force a clean reload (watchers usually pick up changes, but a restart guarantees a fresh state).

## Basic Steps

1. **Pick the service identifier**
   - Choose a readable slug (`kebab-case`) that becomes the public ID (`services/my-service`).
   - Keep the ID stable; workflows reference it directly.

2. **Create the folder and package**

   ```bash
   mkdir services/my-service
   cd services/my-service
   pnpm init
   ```

   Then edit `package.json` so it looks like:

   ```json
   {
     "name": "my-service",
     "version": "1.0.0",
     "type": "module",
     "dependencies": {
       "@area/sdk": "workspace:*"
     }
   }
   ```

   The `"type": "module"` flag is required because the backend loads the file via `import()`. The `@area/sdk` dependency gives access to the helpers `createService`, `createAction`, `createReaction`, `createWebhook`, and more.

3. **Write `index.ts`**  
   Start with a minimal skeleton:

   ```ts
   import { createService } from "@area/sdk";

   const SERVICE_ID = "my-service";

   export default createService({
     id: SERVICE_ID,
     name: "My Service",
     version: "1.0.0",
     description: "Short description shown to users.",
     logo: "https://example.com/logo.png",
     auth: { type: "none" }, // or oauth2 / api_key
   });
   ```

   - `logo` expects a public URL (displayed in the UI).
   - `auth` must describe how users authenticate:
     - `none`: no authentication required.
     - `api_key`: provide `keyName`, `keyLocation`, and optionally `description`.
     - `oauth2`: supply `authorizationUrl`, `tokenUrl`, `scopes`, `clientIdEnvVar`, `clientSecretEnvVar`. Environment variables are read by the backend.

4. **Add actions, reactions, or webhooks**  
   Full example:

   ```ts
   import {
     createService,
     createAction,
     createReaction,
     createWebhook,
   } from "@area/sdk";

   export default createService({
     id: "my-service",
     name: "My Service",
     version: "1.0.0",
     description: "Does something remarkable.",
     logo: "https://example.com/logo.png",
     auth: { type: "none" },

     actions: [
       createAction({
         id: "event-detected",
         name: "An event is detected",
         description: "Triggers the workflow when the event occurs.",
         input: { filter: "string" }, // configurable parameters in the UI
         output: { value: "string" }, // data forwarded to reactions
         run: async (params, ctx) => {
           // Return null when nothing should trigger,
           // otherwise return data that matches `output`.
           return { value: `Trigger for ${params.filter}` };
         },
       }),
     ],

     reactions: [
       createReaction({
         id: "do-something",
         name: "Do something",
         description: "Executes a concrete side effect.",
         input: { message: "string" },
         output: { ok: "boolean" },
         run: async (params, ctx) => {
           ctx.logger?.log?.(
             `[my-service] Reaction executed with: ${params.message}`,
             "MyService",
           );
           return { ok: true };
         },
       }),
     ],

     webhooks: [
       createWebhook({
         id: "events",
         name: "Events webhook",
         description: "Raw ingestion of external webhooks.",
         output: { received: "boolean" },
         run: async (_event, payload, ctx) => {
           ctx.logger?.log?.(
             `[my-service] Webhook received: ${JSON.stringify(payload)}`,
             "MyService",
           );
           return { received: true };
         },
       }),
     ],
   });
   ```

   Key points:
   - Identifiers (`id`) must be unique within the service and match `[a-zA-Z0-9_-]`.
   - `input`/`output` describe the schema shown in the UI; use the primitive types `string`, `number`, `boolean`, `object`.
   - Returning `null` from an action means “nothing to trigger” (useful for polling logic).
   - Use `ctx.logger` for observability; messages surface in the workflow run viewer.

5. **Handle user connections (optional)**
   - `onConnect` runs right after a user links the service (helpful to validate a token).
   - `onDisconnect` lets you clean up remote resources when connections are revoked.
   - For webhook-driven actions, rely on `ctx.webhookEvents` to read persisted events and mark them as processed (see `services/github` or `services/test-webhook` for real examples).

6. **Verify the service is detected**
   - Restart the backend (`pnpm --filter backend dev`) or wait for watchers to refresh.
   - Inspect `GET /about.json` (with `curl`, Postman, or the “About” panel in the web app): the new service should appear under `server.services`.
   - Exercise a full workflow to confirm actions and reactions behave as expected.

## Going Further

- **Manifest-only service**: you can create `services/my-service/manifest.json` that follows the schema in `apps/backend/src/services/manifest.types.ts`. This fits when the service has no custom logic; otherwise provide an `index.ts` exporting either a `PluginHandler` or a service built with `@area/sdk`.
- **Extra dependencies**: add any library you need to the service’s `package.json`, then rerun `pnpm install` at the root so the workspace picks it up.
- **Deployment**: ensure every required environment variable (for example, `GITHUB_CLIENT_ID_ACTION`, `GITHUB_CLIENT_SECRET_ACTION`) is set in the target environment before shipping the service.
